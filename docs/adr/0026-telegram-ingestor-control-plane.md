# Telegram 采集器管理控制面

> 状态：已接受（2026-09-04）

Telegram 个人账号 session 是长期敏感凭据，而管理端需要提供首次绑定、二维码重新授权、来源预解析确认和日常采集控制。如果 API 进程直接读取 session，或把验证码、密码、二维码 token 放入持久队列，账号凭据边界会扩大且授权中断后会留下不应恢复的敏感状态。

项目决定由唯一的 `telegram-ingestor` 进程独占正式 session 和每次授权的临时 session。API 通过带部署级共享令牌的 Docker 内网控制通道访问采集器；浏览器只能调用受现有 `admin` 权限保护的 `/api/v1/admin/telegram/*` 接口，永远不能获得控制令牌、session 文件或原始 `tg://` 二维码链接。控制端口不映射到宿主机，验证码、Telegram 二次验证密码、二维码 token、私密邀请 token 和管理员确认票据均只存在于短期内存或当前请求中。

授权会话全局单例。首次绑定必须使用配置手机号的验证码；二维码只允许用于已绑定账号的重新授权，并且成功返回的 Telegram 用户 ID 必须与既有绑定一致。授权开始时运行时停止新的 Telegram 读取并受控排空，临时 session 只有在身份校验成功后才原子提升为正式 session。取消、失败、过期或账号不一致会丢弃临时 session，保留旧正式 session 和既有账号状态。

来源不再由管理 API 直接接受原始 `chat_ref` 后写入数据库。页面先预解析，管理员确认后由采集器重新校验访问权限，服务端只保存 canonical chat ID 和非敏感展示信息。私密邀请在预解析与确认两个阶段都要求当前管理员密码和页面二次确认，因为确认可能使采集账号加入对象。来源暂停、恢复、失败恢复和重新回填通过服务层原子更新来源状态并追加脱敏审计；日常运维不允许以手工 SQL 或清空 Redis 代替这些状态转换。

该决策将 Telegram 管理台固定为一个受控的操作工作区：账号状态、采集器心跳和来源状态分别表达身份、运行进程和同步生命周期；页面可观察而不承担容器生命周期或部署级密钥管理。它取代旧的交互式 `telegram-ingestor -mode login` 和管理 API 直接创建来源作为常规操作路径的约定。
