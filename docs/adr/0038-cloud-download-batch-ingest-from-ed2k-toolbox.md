# 从 ED2K 工具箱发起云下载批量入库

## 背景

当前 115 云下载是**两段式**：管理员在 `admin ED2K 链接生成器` 粘贴、勾选、确认后只创建[[115 云下载任务]]（`docs/adr/0029-explicit-batch-cloud-download-from-ed2k-toolbox.md`），任务完成后还必须去 `115 云下载任务` 列表逐条点「入媒体库」并填一遍视频类型、标题、合集（`docs/adr/0030-explicit-cloud-download-import-into-media-library.md`）。一批 30 条链接意味着 30 次弹窗。

管理员需要的是**一条龙**：一次点击完成"提交 115 → 下载到本地 → 带元数据入库"。

这次同时越过两条既有边界，必须在 ADR 里写明而不是让下一个人从代码里猜：

- ADR 0029 写死了「批量不是新的任务实体，不新增 batch 表、不引入聚合状态」。
- ADR 0030 写死了「入库必须由管理员在任务列表显式发起」。

## 决策

### 入口与范围

- **只在工具箱新增独立按钮**「批量入库」，与既有「发送选中到115」并列，不合并、不互斥替换。旧按钮语义完全不变（只投递、不入库）。
- **只作用于 `/toolbox/ed2k`**。论坛资源列表与 Telegram 论坛下载保持逐条「只下载」，不获得自动入库能力。
- 正式术语是**云下载批量入库**，与既有的**压缩包批量入库**（`ArchiveImportWorkspace`）区分；按钮文案可用「批量入库到媒体库」。
- 单批上限沿用 50 条（与批量提交同一条校验）；超过 20 条时确认框提示「本批将占用 N 个下载槽位」。

### 准入判定

- **「单文件」是免费的**：ED2K 只接受 `|file|` 段，解析层已保证单文件，不需要另判。
- **只判是不是视频**，扩展名白名单直接复用 `admin-web/src/views/videoUpload.filename.js` 的 20 项（mp4/mkv/avi/ts/mov/wmv/flv/webm/m4v/rmvb/rm/3gp/mpg/mpeg/m2ts/mts/ogv/asf/f4v/vob），不另立第二份真相。
- **三分法**，不是二分：
  1. **视频**（白名单内）→ 放行。
  2. **明确不是单文件视频**（压缩包、图片、其它已识别媒体）→ 排除并给确定原因，**不询问**；压缩包指向「压缩包批量入库」工作台。
  3. **无法识别**（无扩展名、未知扩展名、文件名被截断）→ 只有这一类进入管理员裁决。
- **不处理图片、不新建图片入库通道**。「图片合集同理」明确不做：`cloud_download_imports.kind` 只有 `video/archive`，图片入库是独立 multipart 链路，不在本次范围。

### 无法识别与强制放行

- 确认框内汇总成一个「无法识别」分区，**默认全部取消**，提供「全部强制按视频」一键，也允许逐条勾选。
- 强制项**媒体类型不由单条决定**，一律按视频——类型是批级设置，若强制项要单独选类型，"一键强制"就退化成逐条填表。
- 强制项在提交结果里用独立标签 `forced`，不混进"已提交"，并在确认框标注「后缀未知，可能下载完成后仍无法入库」。
- 理由是**入库的类型判断看内容不看后缀**：导入时先按 MIME 判压缩包、再用 ffprobe 找视频流（`internal/services/cloud_download_import_service.go:150-172`）。"强制"只承诺照常下载，不承诺入库成功。

### 提交前检查

- 只查两层：**任务层**（本库 `cloud_download_tasks` 同 `info_hash`）与**库层**（`FindVideoByHash(hash, size)`）。
- **不新建 115 目录查询能力**。`internal/cloud` 当前没有目录浏览/文件列表能力（只调会话校验、配额、`get_id`、提交离线、任务列表、删除），查"115 里是否已有同名文件"是需要立项的新能力，且文件名会被 115 改写，同名不等于同文件。
- 命中行为：

  | 命中 | 行为 |
  |---|---|
  | 云任务 `completed`、未入库 | 跳过下载，直接按本批前置要求入库 |
  | 云任务进行中 | 不重复提交，标记等待，下载完成后仍按本批前置要求入库 |
  | 云任务 `failed`/`blocked` | 视为显式重试（沿用 ADR 0029） |
  | 视频库已存在（`hash+size`） | 追加视频合集后跳过，复用 ADR 0037 的幂等并集语义 |

### 入库前置要求

- 元数据是**整批一份**，字段等价于**上传视频页面的入库前字段**（不含文件选择）：视频类型（默认 `short`）、AV 地区（仅 `av`，默认 `japanese`）、标题模式、描述、标签、视频合集（多选、仅 `short`、可现场新建）、关联演员、图片图集（单选、只能选已有，因为上传页也只具备这个能力）。
- **标题模式**两种：整批共用一个统一标题，或每条按声明文件名清洗。
- 确认列表**逐条只读展示算出来的最终标题**，让用户在点确认前就能看出清洗是否出错；不提供提交前逐条编辑（那是逐条上传的活）。
- **类型与合集互斥**：选非 `short` 时隐藏并清空视频合集，完全对齐 `VideoUpload.vue:90-127` 的既有联动，不放开后端 `ErrCollectionsOnlyForShort` 限制。
- **不引入集数字段**；`episode` 只是一个类型值。

### 标题清洗

- 新写一个纯函数，规则依次为：
  1. 剥白名单扩展名（用同一份 20 项清单）；
  2. 删域名水印（`www.98t.la@`、`98T.la@`、`hhd800.com@` 一类）；
  3. 去掉成对包裹的站点/画质/语言类标签（`【】`、`[]`、`()`），保留有信息量的括号内容；
  4. 去掉末尾的 `- 副本`、`(1)`、`_2` 这类重复下载后缀；
  5. 分隔符归一为**单空格**。
- **不删除画质与编码标记**（1080p/720p/4K/x264/HDR）：误删伤标题，且它们无害。
- 该函数**只服务新的批量入库链路**。既有 4 套标题实现（`videoUpload.filename.js` 的"替换成点号"、压缩包前后端两套"保留标点"、云导入的"只去扩展名"）**不在本次收敛**，收敛它们是独立任务。

### 一条龙与自动入库

- 任务下载落盘（`status=completed`）后，**自动**执行与人工「115 云下载导入」完全相同的导入动作，不再需要管理员去列表页点。
- 自动入库**只对入库批成员生效**；其它来源（论坛、Telegram、手动单条）仍走显式导入。
- 强制执行**不走滚动投递**：一次把整批入队，不采用"投 N 条、完成一条补一条"的隐性取消机制。

### 入库批实体（推翻 ADR 0029 的"无 batch 表"）

- 新增 `cloud_ingest_batches`（批级前置要求 + 汇总状态）与 `cloud_download_tasks.ingest_batch_id`（可空外键）。
- 理由：批级元数据必须原子地套用到 N 条任务；若每条复制一份，中途失败会留下"一半挂这个合集、一半挂那个"。批级筛选与结果汇总也需要一个稳定标识。
- **批不是新的下载执行单元**：下载仍按即有的单条 [[115 云下载任务]] 状态机执行，队列与重试语义不变。

### 不做取消

- **不新增 `cancelled` 状态、不提供批取消、不采用滚动投递**。
- 后果：误提交只能去任务列表逐条删除本地文件或移入 115 回收站，已在下载的任务无法从工具箱停止。
- 已在 `CONTEXT.md` 记为已知边界，而非待办。

### 可观测

- 进度**以现有 `115 云下载任务` 列表为唯一真相**，加「入库批」筛选与「入库状态」列；不新建第二套进度页、不做工具箱内轮询。
- 提交后跳转到该列表并带批筛选，让管理员当场看到自己这一批。

## 与 ADR 0028 / 0029 / 0030 的关系

- **ADR 0021 的"禁止自动副作用"没有被突破**：粘贴、勾选、全选仍然不产生任何副作用；入库批由一次显式点击 + 一次确认框创建。变的是**确认框的承诺范围**——从"我受理了这些投递"变成"我承诺这些会被入库"。
- **ADR 0029 的两条被局部推翻**：新增 batch 实体；单条任务不再是唯一实体。但"逐条结果、单条失败不中断整批、按 `info_hash` 全局唯一、`failed/blocked` 视为重试"全部保留。
- **ADR 0030 的显式原则保留**：自动入库不是全局开关，只对显式创建的入库批生效；人工导入入口继续存在且继续是论坛来源的唯一途径。
- 论坛列表、Telegram 论坛下载不受影响。

## 考虑过的替代方案

- **复用单任务导入弹窗逐条走**：N 条链接要 N 次弹窗，失去"一条龙"的意义。
- **全局开启下载完成自动入库**：会让论坛与 Telegram 来源也自动入库，直接违反 ADR 0030 的显式原则。
- **新建 115 目录查询以判断"云里是否已有"**：需要新能力，且文件名会被改写，误判成本高于收益。
- **滚动投递 + 停止补投来代替取消**：等于给了一个没有状态、没有筛选、没有结果汇总的隐性取消，比不做更糟。
- **给图片也开一条 115 入库通道**：`kind` 缺 image、内容探测缺图片分支、图片侧连新建合集都没有，成本高一个量级，拆成独立需求。
- **全量收敛 4 套标题清洗**：会改动已上线的上传行为，属于独立任务，本次只保证新链路内部一致。

## 后果与风险

- **强制项可能白下**：后缀未知的条目放行后仍会被内容探测拒绝，单条最多浪费一个 6 小时下载槽位。
- **无止损**：误提交或选错合集后只能逐条删除；50 条批的上限让误操作代价可控但不可忽略。
- **已导入不可重导**：`cloud_download_imports.task_id` 唯一，已导入的批成员再次提交直接返回旧记录，合集挂错无法用本功能修正。
- **`info_hash` 唯一但无账号维度**：换 115 账号后旧任务行仍会挡住同一链接。
- **批内同名文件会互相踩**：`savepath` 恒为空、115 目标目录全局唯一，本地下盘也在单层 `DOWNLOAD_DIR` 里靠"重名加序号"匹配，同一发布组的多条同名链接可能认错文件。
- **标题存在两套语义**：新链路与上传页对同一文件可能产出不同标题，属已知技术债。
- **自动入库沿用现有状态机**：导入失败进入 `failed` 可重试，但重试入口仍在列表页，批级"整批重试"不存在。
- 本次不改 Android/TV，仅管理端与服务端。
