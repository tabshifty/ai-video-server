# 管理端从 ED2K 工具箱显式批量提交到 115 云下载

## 背景

`CONTEXT.md` 原先把 `admin ED2K 链接生成器` 定义为纯浏览器端工具：只把管理员粘贴的多行 `ed2k://` 文本转成可点击链接，不把 ED2K 内容提交到后端。`docs/adr/0028-explicit-cloud-download-from-forum-resources.md` 又规定论坛列表只允许逐条「发送到115」，一次只提交一条链接。

管理员现在需要把工具箱里已经粘贴、核对过的多条 ED2K 一次性交给 115 云下载。这个动作仍然是**管理员显式发起**的：粘贴、勾选、全选都不产生副作用，必须再点「发送选中到115」并确认。它不改变 ADR 0021 要阻止的“自动批量抓取/隐式副作用”边界。

## 决策

- **只从工具箱提供批量入口**。论坛列表仍保持逐条动作，不做行级批量；工具箱的批量能力不反向扩展到论坛列表。论坛列表的按钮样式调整不改变“逐条”语义。
- **单批最多 50 条**，前端与后端双重校验；超过上限直接拒绝并提示缩减选择，不静默截断。
- **批量不是新的任务实体**。每条链接仍对应一个独立的 `115 云下载任务`，以 `info_hash` 全局唯一；不新增 batch 表、聚合状态或“整批重试”。
- **批内去重**：同一 `info_hash` 只提交一次，后续条目返回 `duplicate`；跨批同一 hash 走已有任务的分类（completed/进行中跳过，failed/blocked 重试）。
- **逐条结果，不中断整批**：`submitted / retried / skipped_completed / skipped_active / duplicate / invalid / failed` 七类；单条失败只标记该条，其余继续。接口只落库和入队，不等待 115。
- **来源只在首次创建时写入**：`source` 为 `forum_post`（论坛列表）、`toolbox`（工具箱批量）、`manual`（无来源帖的单条入口）。后续对同一 hash 的重试不覆盖来源。帖子删除后 `post_id` 会变为 `NULL`，`source` 仍保留原入口。
- **云下载任务使用独立 `cloud` asynq 队列**，权重 1；server 与 worker 必须使用同一个 `CLOUD_DOWNLOAD_QUEUE`（默认 `cloud`）。权重只降低云下载抢占转码槽位的概率，不是并发上限；单个任务仍可能占用一个 worker 槽位最长 6 小时。
- **功能关闭时保持路由可辨识**：`/api/v1/admin/cloud-downloads/*` 仍注册，由 `requireCloudDownload` 统一返回 503；worker 不注册 `cloud:download` 处理器、也不消费 `cloud` 队列。这样管理端能显示“云下载功能未启用”，而不是把 404 当成参数错误。
- 工具箱新增全选/逐行勾选、50 条上限、确认框（选中/无效/重复/已存在/将重试/将提交）和逐条结果；失败/无效项保留勾选，管理员可再次点同一按钮重试。进度仍以云下载任务列表为准，工具箱不轮询。

## 与 ADR 0021 / 0028 的关系

- ADR 0021 仍然约束**自动**行为：加载、刷新、翻页、点击链接本身都不得创建下载任务。工具箱批量必须由管理员显式点击并确认，不属于自动行为。
- ADR 0028 的“一次只提交一条”只适用于**论坛列表**；工具箱的显式批量由本 ADR 约束。两条路径共用同一套任务状态机、`info_hash` 去重和失败恢复逻辑。
- 论坛列表仍不展示右侧操作列；本次只把行内按钮从链接样式改为普通按钮，动作粒度和位置不变。

## 考虑过的替代方案

- **前端循环调用单条接口**：不新增后端接口，但会产生 N 个请求，无法统一限制 50 条、无法在服务端做批内去重和逐条结果；并发和错误处理也更差。
- **新增 batch 实体和聚合状态**：需要额外的表、状态机和恢复逻辑，且 115 侧仍是逐条任务，聚合状态很难可靠映射；首期不做。
- **粘贴/全选即自动提交**：正是 ADR 0021 要阻止的隐式批量副作用。
- **继续复用主队列**：批量提交可能一次占满多个 6 小时槽位，饿死转码和解包；改用独立低权重队列。
- **功能关闭时直接不注册路由**：前端只能拿到 404，无法区分“功能关闭”和“路径错误”；改为统一 503。
- **本次就做论坛右侧操作列**：需求已确认延期，避免把“逐条”语义和列布局改造混在同一次变更里。

## 后果与风险

- 新增 migration `0044_cloud_download_source`（additive，默认 `forum_post`；旧二进制省略该列时仍可写入）。
- 新增 `POST /api/v1/admin/cloud-downloads/batch`；单批最多 50 条，响应逐条结果和 summary。
- 新增 `cloud` 队列；只重启 server 不重启 worker 会导致任务投递后无人消费，部署时必须同时重启两者。队列权重不是硬隔离；需要严格隔离时应另起 worker 或增加信号量。
- 批量接口只表示“本次逐条受理结果”，不表示任务完成；进度仍看任务列表。批量任务来源为 `toolbox`，任务列表的“来源”列会显示“工具箱”。
- 关闭功能时旧任务不会被 worker 消费；重新开启后会由 reconciler 恢复。部署过渡期同一 task 可能短暂同时存在于主队列和 cloud 队列，依赖 115 `10008` 幂等和 `download_triggered_at` 一次性 claim 兜底。
