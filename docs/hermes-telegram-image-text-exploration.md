# Hermes 定时推送图文合并：需求讨论

## 目标

用户要求 Hermes 定时任务发送的 Telegram 消息将文字和图片放在一起。按 grill-with-docs 完成调查后，用户确认以下方案并开始实施。

## 已核实的源码事实

- `integrations/hermes-forum-download/bridge.py` 的 `send_post()` 提取媒体和文字后，先以空文字参数调用 `_send_telegram()` 发送媒体，再调用 `bot.send_message()` 发送文字，故该路径会产生独立的图片和文字消息。
- 下载按钮绑定在最后一段文字消息上；资源选择和确认交互使用 `edit_message_text()`。改成图片说明文字后，需要同步设计按钮交互，不能只把发送参数拼在一起。
- 当前文字以 UTF-16 长度 3500 分段；不能直接把该分段上限用于图片说明文字。
- 活动 Hermes 已启用 `forum-download` 扩展；新帖含 ED2K 时切换到 `forum-download-send`，历史补漏复用通知投递逻辑。仓库源码与 Hermes 活动运行文件独立发布，后续修改需要独立安装。
- 当前每帖仅有一个 `preview_media`，本轮无需新增多图策略。文字包括标题、帖子链接、最多十条附件及十条 ED2K 和来源，因此存在超过图片说明文字容量的情况；当前通知队列为空，无法据此统计近期长度分布。
- Hermes 通用发送器已经支持单图短文字作为图片说明发送；扩展主动传入空文字，绕过了此能力。

## 已确认的展示边界

1. 单张预览图与短文字合并；超过图片说明容量时，保留标题、帖子链接和资源数量摘要，不另发溢出正文。完整 ED2K 通过资源按钮查看，附件通过帖子链接查看。
2. 入口按钮放在图文下；单资源「下载」或「重试下载」直接提交，多资源「选择下载」才打开独立回复面板，后续分页和确认编辑面板，保留原始图文；历史消息按钮维持兼容。
3. 无图或图片发送失败时回退完整文字，保留资源入口；不追溯修改历史推送，不主动补发测试消息。
