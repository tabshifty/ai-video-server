# PRD 草案：日本 AV 元数据目录

> 状态：需求访谈中。本文只固定已经确认的目标和决策门禁，不代表已批准实施。

## 目标

建立可长期运行的日本 AV 元数据采集与维护能力，从明确允许访问的来源获取影片标题、封面、分类、演员、剧情简介等公开元数据，支持增量同步、去重、来源追踪、人工纠错和失败恢复。

## 已知现状

- 现有 `videos` 模型服务于已经上传到本地媒体库的视频，不等同于完整的外部影片目录。
- 现有刮削服务已经支持多站点搜索和详情解析、候选确认、演员关联、封面下载、文本翻译及抓取诊断。
- 现有异步任务适合单个本地视频的刮削，不具备站点目录发现、游标推进、定期回查和大规模采集治理能力。

## 暂定范围

- 影片字段候选：标准番号、原始标题、中文标题、剧情简介、发行日期、时长、片商、厂牌、系列、分类、演员、导演、封面与样例图片。
- 来源字段候选：来源代码、来源条目 ID、详情 URL、首次发现时间、最后抓取时间、内容更新时间、抓取状态和原始字段快照或指纹。
- 运维能力候选：来源开关、限速、并发控制、增量游标、失败重试、断点续跑、数据冲突查看、手动修复和来源健康状态。
- 数据质量候选：番号规范化、同片去重、演员别名归并、字段级来源优先级、删除或下架处理、历史变更审计。

## 强制边界

- 只采集经确认允许自动访问或通过正式 API 提供的数据；遵守来源条款、`robots.txt`、访问频控和版权要求。
- 不绕过登录、付费墙、验证码、反爬措施、地域限制或访问控制，不购买或共享抓取账号。
- 不采集、保存或展示任何可能涉及未成年人的成人内容；来源无法提供可靠成年保证时不得接入。
- 封面和样例图片是否允许本地保存必须逐来源确认；不默认把“网页可见”等同于“允许复制和再分发”。
- 所有字段必须可追溯到具体来源和抓取时间，人工修改不得被后续同步静默覆盖。

## 必须先决策的问题

1. 产品范围：仅为本地已有视频补全元数据，还是保存没有本地视频文件的完整外部目录？
2. 使用范围：仅家庭私有使用，还是可能提供公网、多人或商业访问？
3. 来源清单：首批网站或 API 是哪些，各自是否允许自动采集、图片缓存和长期保存？
4. 覆盖规模：只追踪新发行、指定厂牌或演员，还是回溯历史全量；目标条目量和每日新增量是多少？
5. 主身份：是否以规范化番号为主要业务键；无码、同番号多版本、合集、重发和 FC2 是否纳入？
6. 字段冲突：多个来源不一致时按字段级优先级、最新时间还是人工确认决定？
7. 图片策略：只保存远端 URL、反向代理缓存，还是下载原图到本地对象存储；允许保留多久？
8. 语言策略：保留日文原文并生成中文译文，还是只展示中文；机器翻译是否必须人工审核？
9. 删除策略：来源条目下架、演员更名或元数据纠正后，目录是保留历史、软删除还是同步删除？
10. 与本地媒体关系：目录条目和 `videos` 是一对多、多对多还是严格一对一；何时自动关联，何时必须人工确认？

## 非目标

- 当前阶段不编写抓取器、不新增数据库表、不批量访问任何外部站点。
- 不采集或托管视频正文、种子、磁力链接、破解内容或付费内容。
- 不以规避网站限制或提高隐蔽性为设计目标。

## 验收条件

- 上述关键问题形成明确答案，并把长期有效结论沉淀到 `CONTEXT.md` 和必要 ADR。
- 每个首批来源都有访问依据、允许字段、图片政策、限速和停止条件记录。
- 数据模型能表达目录条目、来源事实、字段合并结果、人工覆盖和本地视频关联，且迁移可回退、旧二进制可继续运行。
- 实施拆成可独立提交和回滚的阶段，每阶段都有自动化验证与人工验收脚本。
